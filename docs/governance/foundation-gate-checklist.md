# Governance Foundation Gate

Status: required before schema, API, AI, or production UI implementation

Use this checklist at the product, design, content, data, security, and board review.

## Product and resident journeys

- [ ] Governance Home has one clear next action in every state.
- [ ] Consultation journey is approved from entry through published outcome.
- [ ] Issue journey includes resident-controlled duplicate handling.
- [ ] Project following and update behavior are approved.
- [ ] Meeting journey distinguishes upcoming, live, processing, draft, and published records.
- [ ] Candidate-question journey includes neutrality, moderation history, and outcome status.
- [ ] Evidence journey includes consent, visibility, metadata, safety review, and non-photo alternatives.
- [ ] My contributions supports status, notification, attribution, and privacy actions.

## Navigation and screens

- [ ] Seven resident destinations are approved at the route level.
- [ ] Five-item mobile dock is approved: Home, Map, Perks, Events, Governance.
- [ ] Card and Profile entry points are approved.
- [ ] Governance works as both a route and map-connected sheet without duplicate content.
- [ ] Every surface supports back, close, history, focus restoration, and safe-area containment.
- [ ] Loading, empty, partial, success, validation, network, permission, closed, archived, completed, offline, realtime, and AI-unavailable states are designed.

## Content and governance

- [ ] DANA approves the neutrality statement.
- [ ] DANA approves the explanation of how resident input informs decisions.
- [ ] Official, community-reported, partner-provided, and AI-draft content labels are approved.
- [ ] Moderation, correction, appeal, archive, and public-record language is approved.
- [ ] No candidate endorsement or candidate-ranking workflow exists.

## Components and design system

- [ ] Every new component maps to Editorial, Directory, or Glass.
- [ ] Every component has one decision-support purpose.
- [ ] No dashboard, bento, nested-card, or government-portal visual language is introduced.
- [ ] Component APIs accept canonical IDs and typed view models.
- [ ] Map and non-map alternatives share the same object data.

## Data and permissions

- [ ] Canonical object list is approved.
- [ ] Relationship roles are approved.
- [ ] Visibility classes are approved.
- [ ] Resident-private, moderation, board-restricted, partner-aggregate, and audit boundaries are documented.
- [ ] Anonymous participation and identity linking rules are approved.
- [ ] Retention, deletion, correction, and public-record obligations have accountable owners.
- [ ] Reporting thresholds prevent individual resident inference.

## Map

- [ ] Governance layer categories are approved.
- [ ] One-object/one-pin rule is approved.
- [ ] Grouped same-location behavior is approved.
- [ ] Official and community-reported status treatment is approved.
- [ ] Objects without verified coordinates remain unpinned.
- [ ] All governance drawers use the shared map panel contract.

## Events and notifications

- [ ] Canonical event envelope is approved.
- [ ] Event taxonomy is versioned.
- [ ] Correlation and causation IDs are required for automated workflows.
- [ ] Object following is separate from marketing consent.
- [ ] Notification channel, frequency, quiet hours, and area preferences are resident-controlled.
- [ ] Every notification links to one canonical object.

## AI

- [ ] OpenAI receives bounded, permission-filtered context only.
- [ ] Deterministic product behavior remains available without AI.
- [ ] Each agent has an allowlist and forbidden-action list.
- [ ] Official output requires named human review.
- [ ] Sources and timestamps appear with factual resident answers.
- [ ] AI drafts, approvals, rejections, and superseded versions are audited.
- [ ] The LLM is not the system of record.

## Accessibility and QA

- [ ] WCAG 2.2 AA review is scheduled.
- [ ] Keyboard, screen reader, reduced-motion, zoom, and high-contrast behavior are specified.
- [ ] Map participation has a non-map alternative.
- [ ] Forms preserve progress and never clear valid answers after an error.
- [ ] Mobile testing covers 320px through 430px widths.
- [ ] No panel can exceed the usable viewport or hide its close action.
